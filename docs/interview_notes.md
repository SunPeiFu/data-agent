# 智能数据探查面试讲解稿

## 项目定位

这个项目不是纯 RAG 问答，而是一个面向数据资产探查场景的 Agent Planner。它负责把用户自然语言问题拆成可执行的数据工具调用计划，再交给 TiDB、Milvus、Neo4j 等工具执行。

## 为什么不是纯 RAG

RAG 适合补充表说明和业务语义，但血缘关系是确定性的图关系查询，不能靠语义召回猜。因此系统把元数据查询、语义召回、血缘查询拆成不同工具，用 Agent 编排层决定何时调用。

## 意图设计

v1 只保留三类有效意图：

- `metadata_search`：查表、主题域、分层、业务含义。
- `lineage_search`：查血缘关系，方向通过 `LineageDirection` 参数控制。
- `impact_analysis`：表变更影响分析，通常需要表定位、血缘查询和语义补充。

不把上游、下游拆成两个意图，是因为它们本质都是血缘查询，只是工具参数不同。这样意图层更稳定，工具层更灵活。

## 三个面试 case

1. 安逸花业务线营销域下 DWD 层关于支付的表有哪些
   - 意图：`metadata_search`
   - 工具计划：TiDB 精确过滤 + Milvus 语义召回 + 结果融合排序

2. 安逸花 dwd 层 dwd.orderInfo 表修改，对下游哪些表产生影响
   - 意图：`impact_analysis`
   - 方向：`downstream`
   - 工具计划：TiDB 表定位 + Neo4j 血缘查询 + 影响分级

3. 营销域下的 dwd 层 userInfo 表修改，关联影响的上游和下游表有哪些
   - 意图：`impact_analysis`
   - 方向：`both`
   - 工具计划：TiDB 表定位 + Neo4j 双向血缘查询 + Milvus 业务语义补充 + 影响结果融合

## 表名解析

表名支持三段式、两段式和一段式：

- 三段式：`catalog.schema.table`
- 两段式：`schema.table`
- 一段式：`userInfo`

一段式表名不能直接判定唯一，必须先通过 TiDB 元数据工具结合业务线、主题域、数仓分层做候选表定位。

## 面试回答模板

我们没有把用户问题直接丢给大模型回答，而是设计了一层 LangGraph Agent Planner。系统先做规则预分析，识别表变更、上下游方向、数仓分层等高确定性信号；再调用 OpenAI-compatible 本地或云端模型做结构化解析，并用 Pydantic 对枚举和类型做校验；最后由 PolicyResolver 合并规则和模型结果。强规则优先，LLM 补充弱语义实体；如果模型不可用或输出不合法，会降级到规则结果。最后系统根据合并后的结构化结果生成工具调用计划。

比如用户问“营销域下的 dwd 层 userInfo 表修改，关联影响的上游和下游表有哪些”，系统会识别为影响分析任务，先用 TiDB resolve 一段式表名，再调用 Neo4j 做双向血缘查询，同时用 Milvus 补充表说明和业务语义，最后由影响分析器做结果融合。
